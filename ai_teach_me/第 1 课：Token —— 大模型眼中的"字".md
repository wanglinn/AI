## 第 1 课：Token —— 大模型眼中的"字"

### 1.1 一个反直觉的事实

先做个实验。你打开终端，运行：

```bash
ollama run qwen2.5:7b
```

然后输入：

```
请分别计算下面两段话有多少个"字"：
1. "我爱北京天安门"
2. "I love Beijing Tiananmen"
```

**你会发现**：模型对中文可能说 7 个字，对英文可能说 5 个单词，但它**实际上看到的不是这些**。

**真相**：模型看到的既不是"字"，也不是"词"，而是 **Token**。

---

### 1.2 什么是 Token？

**Token 是模型处理文本的最小单位**，介于"字"和"词"之间。

| 你看到的 | 模型实际看到的 Token | 说明 |
|---|---|---|
| 我 | `我` | 单字就是一个 token |
| 爱 | `爱` | |
| 北京 | `北京` | 常见词会被合并成一个 token |
| 天安门 | `天安门` | 更长的常见词也是一个 token |
| I | `I` | 英文单词通常一个 token |
| love | `love` | |
| ing | `ing` | 但 "loving" 可能被拆成 `lov` + `ing` 两个 token |

**类比数据库**：
- 如果数据库按"行"存储，**Token 就是"行"**
- 但这里的"行"不是固定长度，是**变长编码**——有的 token 是 1 个汉字，有的是 3 个汉字，有的是半个英文单词

---

### 1.3 为什么要切分？直接按字处理不行吗？

**效率问题**。

假设直接按"字"处理：
- 中文约 10 万字，英文约 100 万词
- 如果每个字/词都是一个独立单位，模型需要记住 10 万~100 万种组合，**计算量爆炸**

**Token 化（Tokenization）** 就是**压缩**：
- 把常见的字组合成 token（如"北京"="1 个 token"而不是"2 个 token"）
- 用 5 万~10 万个 token 就能覆盖 99% 的日常文本
- **序列变短了，计算量指数级下降**

**类比**：就像数据库的**列式存储**——不是存整行，而是把常用的列压缩在一起，查询时只读需要的列。

---

### 1.4 BPE：Token 的"压缩算法"

主流大模型（GPT、Qwen、Llama）都用 **BPE（Byte Pair Encoding，字节对编码）**。

**核心思想**：**出现频率高的字组合并成一个 token**。

**训练过程**（简化版）：
1. 准备海量文本，先切成最小单位（如单个字符）
2. 统计：哪两个相邻单位出现最频繁？比如"北"和"京"总是一起出现
3. 合并：把"北京"变成一个新 token
4. 重复：再看现在哪两个 token 最频繁？比如"北京"和"天"经常一起，合并成"北京天"
5. 直到达到预设的词汇表大小（如 5 万个 token）

**结果**：
- 常见词："天安门" → 1 个 token
- 罕见词："犇羴鱻" → 可能 3~4 个 token（拆成认识的部件）
- 英文："unbelievable" → `un` + `believ` + `able`（3 个 token）

---

### 1.5 关键影响：为什么这很重要？

#### 影响 1：上下文窗口按 Token 算

你说你的模型是 7B，它通常有 **32K token 的上下文窗口**（约 2 万~3 万汉字）。

- 不是"能记住 3 万字"，而是"能记住 3 万 token"
- 如果文本里生僻词多，实际能装的汉字更少

#### 影响 2：计费按 Token 算

API 调用通常按 **输入 Token 数 + 输出 Token 数** 计费。

- 你发一段 1000 字的文章，可能只有 700 个 token（因为合并了）
- 模型回复 500 字，可能是 800 个 token（因为拆分了）

#### 影响 3：模型的"字数感"很怪

```bash
# 实验：让模型数"草莓"里有几个"r"
ollama run qwen2.5:7b
>>> "strawberry" 这个单词里有几个字母 r？
```

模型经常答错。因为它看到的不是 `s-t-r-a-w-b-e-r-r-y`，而是 `str` + `aw` + `berry` 之类的 token，**它真的"看"不到单个字母**。

## 🔬 今天的小实验（10 分钟）

### 实验 1：观察 Token 切分

```bash
ollama run qwen2.5:7b
```

输入：

```
请把下面这段话切成 token，用 | 分隔，并解释你的切分逻辑：
"我爱北京天安门，但不喜欢吃香菜"
```

**你会看到类似**：
```
我 | 爱 | 北京 | 天安门 | ， | 但 | 不 | 喜欢 | 吃 | 香菜
```

注意：
- "北京"没有被拆成"北"和"京"
- "天安门"是一个整体
- "不喜欢"可能被拆成"不"和"喜欢"，而不是"不喜"和"欢"

### 实验 2：对比中英文的 Token 效率

```bash
>>> 分别计算下面两段话的 token 数量（估算）：
1. "人工智能正在改变世界"
2. "Artificial intelligence is changing the world"
```

**通常结果**：中文 8~10 个 token，英文 6~8 个 token。**英文通常更省 token**，因为英文单词之间有空格，天然好切分；中文需要更复杂的合并策略。

### 实验 3：观察"幻觉"的根源

```bash
>>> 请精确重复下面这句话，不要改一个字：
"苟利国家生死以，岂因祸福避趋之"
```

如果模型记错了某个字，不要惊讶——它存储的是**概率模式**，不是**精确文本**。就像数据库的**有损压缩**，还原时可能略有偏差。

---

## 📊 Token 与数据库的类比总结

| 数据库概念 | Token 概念 | 你的理解优势 |
|---|---|---|
| 变长字段（VARCHAR） | 变长 Token | 你懂变长存储的 trade-off |
| 编码（UTF-8） | BPE 编码 | 都是"用更少的单位表示更多信息" |
| 页（Page）大小限制 | 上下文窗口限制 | 都是"单次操作的最大粒度" |
| 索引压缩 | Token 合并 | 都是"高频项合并加速查询" |
